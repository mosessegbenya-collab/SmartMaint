# Clerk callback correction — 2026-10-25

Inspected installed Expo **57.0.31**, Expo Router **57.0.29**, `@clerk/expo` **4.13.0**, and its installed `@clerk/react` **6.17.8**. Existing staged/unstaged work was preserved. No dependencies were upgraded for this fix.

## Cause and implementation

The app had no `/sso-callback` route. Web was invoking the Expo browser-session `useSSO()` flow, which defaulted to that missing path. The installed root `useSSO` implementation uses Clerk's legacy auth resources; its native callback also reloads the SDK-managed verification response before returning a session for activation.

- Added the public `src/app/sso-callback.tsx` route and platform-specific implementations outside `src/app`.
- Web initiates a full browser redirect through the installed, supported `@clerk/expo/legacy` `signIn.authenticateWithRedirect` API with an explicit `/sso-callback` target and `/access/pending` completion target.
- The browser callback calls and awaits `clerk.handleRedirectCallback`. Clerk retains responsibility for callback validation, cookies, transfers, session activation and handshake navigation. App fallback routing happens only after that operation completes and an activated/pending identity session exists. SDK-requested handshake navigation is preserved and is never overridden by an early application redirect.
- Callback/continuation views stay outside the operational Convex provider's session-key remount boundary, preventing session activation from remounting and replaying the handshake. The Clerk provider remains mounted. These public views use the default locked staff context; they cannot open protected workspace routes.
- Added web Clerk continuation UI for additional sign-in factors, sign-up requirements, challenges and pending session tasks. Task completion leads to account status. Pending tasks and unapproved accounts cannot authorize workspace access.
- Loading, timeout, cancellation and errors have generic safe messages. Callback inputs and raw SDK errors are not displayed, parsed, copied into state, logged or persisted by app code. The SDK alone processes its callback material. Tests use redacted labels only.
- Native still uses `useSSO` and its supported browser-session processing. Its redirect is now explicitly generated with the `smartmaint` scheme and `sso-callback` path, which has a real route. `setActive` must succeed before app navigation. Cancellation, missing sessions and activation rejection do not navigate as authenticated users. Native browser handoff is separate from the web callback handler.
